## 1. 存在不需要 NPU 的运行通路（推翻旧结论）

官方样例支持 CPU 调测模式与 NPU 仿真模式，且**明确覆盖 dav-2201**：

```
cmake -DCMAKE_ASC_RUN_MODE=cpu -DCMAKE_ASC_ARCHITECTURES=dav-2201 ..;make -j;  # CPU调测模式
cmake -DCMAKE_ASC_RUN_MODE=sim -DCMAKE_ASC_ARCHITECTURES=dav-2201 ..;make -j;  # NPU仿真模式
```

出处（多例一致）：
- `kb/corpus/asc-devkit/examples/01_simd_cpp_api/03_basic_api/03_matrix_compute/batch_matmul/README.md:187-188`
- `kb/corpus/asc-devkit/examples/01_simd_cpp_api/04_advanced_api/00_matmul/matmul/README.md:84-85`
- `kb/corpus/asc-devkit/examples/01_simd_cpp_api/04_advanced_api/04_reduce/reducemax/README.md:90`
- `kb/corpus/asc-devkit/examples/01_simd_cpp_api/04_advanced_api/04_reduce/sum/README.md:82`

能力清单里也直接写了「NPU 调试 / CPU 调试」：`notes/strategy-cannlab.md:17`

**旧结论错在哪**：`ci/watch.sh` 用默认（npu）模式跑组委会 `run.sh`，于是 `aclInit` 失败
`ret=500000`（`notes/ci-loop.md:23`），据此得出"CPU 实例只能编译不能运行"。
**那只是没加 `-DCMAKE_ASC_RUN_MODE=cpu`**，不是环境不行。

### 已决（2026-09-23 二次取证，补抓 `01_utilities` 后）

故当时只能给出"文档承诺、语义未证"。补抓后结论如下，**均为 A/B 级**：

**关键消歧（此前子代理标记为"语料无法解释"）**：`06_cpu_debug/cpu_debug.asc` 是官方 CPU Debug 样例，
其 `main` 中 `aclInit(nullptr)`(`:64`)、`aclrtSetDevice`(`:65`)、`aclrtCreateStream`(`:66`)、
`aclrtMalloc`(`:68-70`) **全部无 `#ifdef` 保护**，且 kernel 用正常 `<<<numBlocks, 0, stream>>>` 启动(`:75`)。

⇒ **CPU 模式下 `aclInit` 与 `<<<>>>` 在主机侧照常工作**；`matmul_fused.asc:283-295` 的
`GmAlloc + ICPU_RUN_KF` 只是另一条可选路径，不是唯一路径。
⇒ 组委会 `main.asc`（`aclInit` + `run_kernel` 内 `<<<>>>`）**在 CPU 调测模式下应当可运行**。

**仍缺**：本机到 CANNLab 实例的投送通道（见下节）。

## 1b. 本机不可直接执行 CPU 调测模式

`-DCMAKE_ASC_RUN_MODE=cpu` 需要 CANN 9.0.0 的 ASC 包与 CPU 调试依赖库。
本机（Windows）无 CANN，故**只能在该模式可用的机器上执行**——即 CANNLab 实例。
本机能做的是：算法模拟、规格校验、编译期静态核对。

## 2. dav-2201 上 L0C→UB 不通，矩阵乘结果必须经 GM

`kb/corpus/asc-devkit/examples/01_simd_cpp_api/03_basic_api/03_matrix_compute/README.md:16`
中 `fixpipe_l0c2ub` 的支持产品列**只有** `Ascend 950PR/Ascend 950DT`；
同文件 `:14` 的 `fixpipe_l0c2gm` 才含 Atlas A2/A3。

⇒ 我们这条 AIC→(GM)→AIV 的通路是**架构强制的**，不是设计选择。

## 3. 计算顺序与精度（纯本地结论）

`work/analysis/sim_kernel.py` 验证：分块覆盖、尾块、四种 transpose、bf16/fp16、
B=64、B=1 全通过。且：

**K 方向累加必须 fp32。** fp16 累加在 K=1024 误差 5.8e-2、K=4096 误差 2.5e-1，
远超判题 gate（rtol=atol=1e-4）。

## 4. 投送通道现状（阻塞）

本机到 GitHub 不通：代理 `127.0.0.1:7890` 在监听，但 HTTPS 连接被关
（`schannel: AcquireSecurityContext ... SEC_E_NO_CREDENTIALS`）。
`git ls-remote` / `git fetch` / `Invoke-WebRequest -Proxy` 全失败。

⇒ **无法从本机 push 驱动云端 CI**。需要换通道（CANNLab WebIDE 浏览器直传，
或 gitcode 镜像，或人工中转）。

## 5. 组委会锁定的 harness 事实

- `problem/template/main.asc:48-56`：本地用例固定 `B=1, M=1, N=1, K=32`，
  x1/x2 各 64 字节，y 4 字节。
- `run.sh:29-42`：只跑 case0，`timeout 120`。
- **本地只有 1 个用例，判题机有 16 个测试点**（用户确认）。本地过 case0 ≠ 过评测。
- `verify_result.py:15`：`("y", float32, rtol=1e-4, atol=1e-4, tol=1e-4)`，
  且对 B≤64 的 y 而言 `tol=1e-4` 等价于**每个元素都要过**。
